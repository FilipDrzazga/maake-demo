From customer file to printed fabric

How the customer portal and RipFlow work together: what happens to a customer's file at every stage, who can see it, when it is deleted, and what it costs to run on Cloudflare compared with WeTransfer.

The whole picture

Today a customer sends the files by WeTransfer and the order as a spreadsheet (CSV), which RipFlow reads in its Custom Order tab; customers whose designs are kept in our library send only the list. With the portal the customer places the order and the file together, the portal checks the file straight away, and RipFlow on our computer picks both up by itself. The customer then follows the order in the portal and gets an e-mail when something changes.

RipFlow always asks the portal; the portal never reaches into the shop's computers. Nothing in the shop has to be open to the internet.

In the print room

One station in the print room, the Cotton PC, asks the portal for new orders once a minute.

For each confirmed order it downloads the customer's file over an encrypted connection, through a short-lived link straight from the portal's storage in the EU; the station's own key is never sent to that storage.

Before the file reaches the print queue, Windows Defender scans it; a file that fails the scan, is damaged, is in a format we cannot print or is larger than 2 GB never enters the queue, and the portal is told, so the customer can send a new file.

Files that pass land in the Inbox on the shop's own server, next to the Etsy and other orders, where an operator picks the files and a printer and creates a print batch; RipFlow then writes the print job for PrintFactory, the printing software.

As the item moves through production, RipFlow reports each step back to the portal: accepted (file received), in production (printed, pressed, checked or at sewing), ready (packed) and shipped.

When a batch is created, the file leaves the Inbox and a print copy is kept in the PRINTED archive on the shop's server, so a print can be repeated.

Old PRINTED batches are deleted only by hand, from a station that has been allowed to do it, and only once they are at least 60 days old.

90 days after an order is finished, RipFlow shrinks its own record of it to the order number, the customer's name and the line ids; an order whose customer was asked for a new file is kept whole, and none of this data leaves the shop.

- written by the RipFlow team

Signing in

Each customer has an account the shop opens for them (by invitation). There are three ways in, and the customer chooses:

Link by e-mail

The customer types their e-mail address and gets a sign-in link. The link works once and only for 15 minutes. The portal keeps only a fingerprint (hash) of the link, not the link itself.

Password

A customer can set a password. It is never stored: the portal keeps only a salted PBKDF2-SHA256 hash (100,000 rounds). Wrong guesses are limited (10 per address in 15 minutes, 50 a day).

Google

A signed-in customer links their Google account once; after that one button signs them in. The portal keeps only Google's account ID, never the Google password.

After signing in the browser keeps a secure session cookie (Secure, HttpOnly - scripts on the page cannot read it). It lasts 30 days and is renewed while the customer uses the portal, but never longer than 90 days after signing in; then the customer signs in again.

The shop's own pages are separate: they sit behind Cloudflare Access, so only the shop's staff and RipFlow stations get in (see Security).

What we keep, where, and for how long

Database (Cloudflare D1, EU)

  • Customer accounts: name, e-mail, delivery addresses, password hash
  • Orders: lines, fabric, quantities, status history
  • Designs: name, thumbnail, size, file fingerprint
  • Mail log and shop audit (90 days)

A copy of the database is exported once a day to the shop's own computer; the last 30 copies are kept.

Files (Cloudflare R2, EU)

  • The customer's print files: PDF, TIFF, JPG or PNG, up to 2 GB each
  • Up to 100 GB per customer at any time
  • Stored only in the EU jurisdiction
  • No payment card data anywhere - the portal takes no payments

Files have no second copy on purpose: the customer always has the original, and a file lives in the cloud only days.

When a file is deleted

A night-time clean-up (03:17 UTC) deletes every file past its time. After that only the design's name and thumbnail stay, so the customer still sees it and can send the file again to reorder.

Security in short

Shop pages

Behind Cloudflare Access: staff sign in through Access, each RipFlow station has its own token. The portal also checks the Access token itself, so no page relies on one gate only.

File downloads

RipFlow gets a signed download link valid for 15 minutes, together with the file's SHA-256 fingerprint and size, so a damaged or swapped file is noticed.

Uploads

The browser sends a big file in 64 MB parts and computes a fingerprint of the whole file. The portal checks the format by the file's content, not its name.

Spending limits

Cloudflare has no hard spending cap, so the portal sets its own: e.g. 20 uploads and 20 orders per customer a day, 60 e-mails a day (10 kept for sign-in links).

Why move from WeTransfer

The file comes with the order

No links in e-mails to match with an order by hand, no expired links. Each file belongs to a customer, a design and an order line.

Checked before it reaches print

Format, size, image resolution (at least 100 dpi for a repeat) and fabric width are checked when the customer sends the file, not when someone opens it.

No typing into RipFlow

RipFlow imports the order and the file by itself. The customer and the shop see the same metres of fabric ("~1.24m").

The customer sees progress

Statuses (Accepted, In production, Ready to ship, Shipped, Needs a new file) and e-mails when they change; "Order again" reuses a design.

Files clean themselves up

Clear rules for how long a file lives, applied every night; files stored in the EU.

Cost grows with use

A fixed fee ($5 Cloudflare, plus $20 if Resend Pro is kept - with the portal's limit of 60 e-mails a day Resend Free is enough) and cents per GB stored; the calculator shows it for any month.

Honest costs and risks. One provider (Cloudflare) runs the program, the database and the files - if it is down, the portal is down. The portal is our own software: someone has to look after it and its updates. The daily database copy lands on a shop computer, so that computer has to be on and backed up.

What we need from the shop

Today the pilot runs on the developer's own private accounts, on a Cloudflare test address. To run it for real customers, every service below should belong to the shop, opened with a shop e-mail address, so that access and billing stay with the business.

1. Cloudflare account

Runs the portal's program, the database, the customers' files (EU) and the lock on the shop's pages (Access). Needs a company payment card for Workers Paid ($5 a month - see the calculator), two-step sign-in and a spending alert. Cloudflare is a US company, so the shop accepts its data processing terms (GDPR) before real customers' data goes in. The portal is then set up again in this account; the project has scripts for it.

2. Resend account (e-mails)

Sends the sign-in links and the order e-mails. The pilot uses Resend's test sender, which delivers only to the account owner's own address - real customers get no e-mail until the shop's account sends from the shop's domain. The free plan is enough at the portal's limit.

3. The shop's domain

An address such as portal.maake.com instead of the test address, and Resend's records for sending from the domain. Both are a few DNS records where maake.com is managed (GoDaddy), added without touching the records of the shop's e-mail (Microsoft 365).

4. Google sign-in

The "Sign in with Google" button uses a sign-in client registered in Google Cloud. It should be registered under the shop's Google account, with the shop's name on Google's sign-in page.

5. Code and backups

The portal's code is in a private GitHub repository on the developer's account; it should move to a shop account or organisation. The daily database copy goes to a shop computer that is on and backed up.

6. People

The staff e-mail addresses allowed into the shop's pages, and one person who receives Cloudflare's and Resend's bills and alerts.
